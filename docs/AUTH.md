# 인증 구현 설명서 — 패스키 잠금 (과제 8)

## ① 무엇으로 붙였나

- **라이브러리 + 직접 구현 조합**
  - 서버: `server/server.ts` — Deno로 직접 쓴 API 서버 (Deno Deploy에서 실행)
  - 서명 검증: `@simplewebauthn/server@13.1.1` — WebAuthn assertion 검증용 표준 라이브러리
  - 저장: Deno KV — 질문(challenge)·세션·공개키·비공개 자료를 서버가 들고 있는 저장소
  - 브라우저: `navigator.credentials` (WebAuthn API) — 패스키 만들기·서명하기
- 비밀번호 입력 칸은 어디에도 없다. "나만 들어가기"의 열쇠는 내 인증기(폰·보안키) 속 개인키뿐.

## ② 왜 그걸 골랐나

- **정적 호스팅으로는 요구사항을 만족할 수 없다.** "서버가 질문을 만들고 보관한다", "로그인 없이 비공개 자료를 요청하면 401/403으로 거절한다", "이미 쓴 질문은 다시 통하지 않는다"는 브라우저 밖에 뭔가가 있어야 가능하다. 그래서 프론트(GitHub Pages) + API 서버(Deno Deploy)로 나눴다.
- **SimpleWebAuthn을 고른 이유**: WebAuthn 검증은 CBOR 디코딩·COSE 공개키·타임아웃·카운터 등 함정이 많다. 라이브러리를 쓰되, 질문 발급·소비·세션·격리 규칙은 전부 직접 구현해 "어디가 내 코드인지"가 명확하다.
- **Bearer 토큰 세션**: 로그인 뒤 사람을 알아보는 수단으로 임의 토큰을 골랐다 — KV에서 바로 무효화할 수 있어 로그아웃이 확실하다.

## ③ 어디를 어떻게 고쳤나 — 네 흐름이 지나는 자리

| 흐름 | 브라우저 쪽 | 서버 쪽 |
|---|---|---|
| **등록** | `private.js` 계정 만들기 → `pk-client.js` `register()` — options 받아 `credentials.create()` 호출, 결과를 JSON으로 전송 | `server.ts` `POST /api/register/options`(질문 발급·KV 보관) → `POST /api/register/verify`(질문 소비 → SimpleWebAuthn 검증 → 공개키 저장) |
| **로그인** | `pk-client.js` `login()` — options 받아 `credentials.get()` | `POST /api/login/options` → `POST /api/login/verify`(질문 소비 → 공개키로 서명 검증 → 세션 토큰 발급) |
| **로그아웃** | `private.js` 로그아웃 버튼 → `PKC.logout()` | `POST /api/logout` — KV에서 세션 즉시 삭제, 이후 같은 토큰은 401 |
| **비공개 자료** | `PKC.privateGet()` — Bearer 토큰으로 조회·저장 | `GET/PUT /api/private` — 토큰 없으면 **401**, 다른 계정 자리면 **403** |
| **패스키 관리** | `private.js` 열린 화면의 목록·추가·삭제 버튼 | `GET /api/passkeys`, `DELETE /api/passkeys/:id`(마지막 하나는 409로 거절) |

서버가 저장하는 것: `chal/`(일회용 질문, 10분), `acct/`(계정), `cred/`(공개키·이름·날짜·카운터), `sess/`(세션, 7일), `priv/`(비공개 항목).

## ④ 안 열리는 것을 확인한 기록

`checks/t08-evidence.json`에 요청/응답 14건을 남겼고, 아래 네 확인 전부 검증했다.

| 확인 | 성공한 요청 | 거절된 요청 |
|---|---|---|
| **로그인 없이 열기** | (없음 — 공개 페이지만 표시됨, 소스에 비공개 내용 0건) | `GET /api/private` 토큰 없음 → **401** |
| **남의 자리 열기** | `GET /api/private` 자기 토큰 → 200 | `GET /api/private?account=테스트` (민기 토큰) → **403**, 반대 방향도 **403** |
| **이미 쓴 질문 재사용** | `POST /api/login/verify` (1회) → 서명 단계 진행 | 같은 본문 2회차 → **401 "만료되었거나 이미 쓴 질문"** |
| **패스키 삭제 뒤 로그인** | 남은 패스키로 `login()` → 통과 | 지운 패스키가 없는 인증기로 `login()` → 거절(등록 자격증명 없음) |

추가 확인: 질문은 매번 다른 값으로 발급됨(두 번 연속 호출 비교), 패스키 목록에 이름·등록일·서명 카운터 표시, 로그아웃한 토큰 재사용 401, 마지막 패스키 삭제 요청 409 거절.

## ⑤ AI와 나

- **AI에게 맡긴 일**: Deno API 서버 전체 작성, SimpleWebAuthn 연동, "나만의 자리" 섹션 UI·클라이언트, 가상 인증기로 전 흐름 자동 검증, 문서·배포 설정.
- **내가 판단한 일**: 과제1 소개 페이지는 공개로 두고 새 구역만 잠그는 경계 결정, 서버 없이는 안 된다는 구조 판단(Deno Deploy 채택), 계정 두 개·패스키 두 개로 검증하는 계획, 마지막 패스키 삭제는 아예 막는 규칙 결정, 비공개 내용은 시연용 예시만 넣는 결정.
- **AI 말을 안 들은 일**: 처음엔 "서버 없이 클라이언트에서만 서명 검증"하는 방향이 나왔는데, 과제 요구(서버 발급 질문·401/403·계정 격리)를 보고 서버 방식으로 설계를 갈아탔다 — 이게 이번 과제에서 가장 큰 방향 전환이었다.

## ⑥ 아직 못 막은 것

1. **XSS로 세션 토큰 탈취**: 토큰을 `localStorage`에 두기 때문에, 페이지에 악성 스크립트가 들어가면 토큰을 빼갈 수 있다. httpOnly 쿠키면 막을 수 있지만, 다른 도메인 간 쿠키라 설정이 복잡해 Bearer를 골랐다 — 인증 서비스 수준까지는 안 갔다.
2. **계정 이름 선점(스쿼팅)**: 계정은 "첫 패스키를 등록한 사람" 것이 된다. 내가 등록하기 전에 남이 같은 이름을 먼저 만들면 막을 방법이 없다(이름 회수 절차가 없다). 실사용 전에 빨리 등록하는 수밖에.
3. **마지막 패스키까지 지운 경우**: 서버는 마지막 패스키 삭제를 409로 막지만, KV 데이터 자체를 지우면 계정은 영구 잠긴다 — 계정 삭제/복구 절차는 없다.
